  • DELETE /leave-requests/{request_id} — Employee cancels a Draft (only while still Draft)

Modified endpoints (minimal, additive changes only — reasons noted inline at each endpoint)

  • POST /leave-requests — same request fields as v1 (leave_type, start_date, end_date), plus an optional attachment file (required when leave_type = Sick, per the medical-report rule). Response status now starts at Draft instead of Pending, matching the spec's Draft → Pending flow (submission is now the new /submit endpoint above).
  • POST /documents/generate — same request fields as v1 (employee_id, doc_type, prompt). Two changes: (1) doc_type value Resignation_Letter is corrected to Termination_Letter — the spec asks for a company-initiated "Termination (Layoff) Letter," which is a different document from an employee-initiated resignation; (2) the response now returns a Draft with editable content instead of an immediate pdf_url, since the spec requires HR review/edit before the document is finalized to PDF or sent by email (see the new /finalize and /send-email endpoints). The 422 missing_employee_data error now returns structured field descriptors (type, label, options) instead of plain field-name strings, per the spec's "structured input fields, not only plain text" requirement.

1. Overview

Wakeel AI is a multi-tenant B2B SaaS. Every company (tenant) has isolated data. The API enforces Tenant Isolation: every authenticated request carries a company_id inside its JWT, and every query on the backend must filter by that company_id — regardless of what the client sends. Clients never pass company_id manually in the request body; it is always derived from the token.

RoleClientTypical Endpoints
Company_OwnerWeb DashboardCompany setup, user invitations, policy upload
HR_ManagerWeb DashboardEmployee records, document generation, leave approval, AI assistant
EmployeeMobile AppOwn profile, AI chat, leave requests, own documents

2. Authentication

2.1 Method

Wakeel AI uses JWT Bearer tokens (access + refresh token pattern). Every JWT payload includes:

{
  "user_id": "uuid",
  "company_id": "uuid",
  "role": "Company_Owner | HR_Manager | Employee",
  "exp": 1721568000
}

Access token lifespan: 15 minutes. Refresh token lifespan: 7 days, stored as an httpOnly cookie (web) or secure storage (mobile).

4.5 Generate a Document (AI-powered) UPDATED

This is the core "AI generates paperwork" feature.

6. AI Assistant Endpoints UPDATED — now shared by HR_Manager and Employee

v1 documented these only under Employee. The spec requires HR to use the same conversational assistant for labor-law questions, policy questions, employee-data questions, and document generation requests — so these are the same two endpoints, now callable by either role. Request and response shapes are unchanged from v1; only the allowed role scope and the retrieval-scoping note below are new.

6.1 Ask the AI Assistant

POST/chat/ask

Request

  "message": "كام رصيد الإجازات باقي عندي؟",
  "language": "AR"
}

Response 200 OK

{
  "chat_id": "ch9d1...",
  "reply": "رصيدك الحالي من الإجازة السنوية هو 16 يوم لعام 2026.",
  "sources": ["employee_leave_balance", "company_policy_doc"],
  "created_at": "2026-07-21T10:20:00Z"

The RAG pipeline's retrieval scope depends on the caller's role:

  • Employee: (1) this employee's own records, (2) this company's policy documents, (3) the general Egyptian Labor Law knowledge base — never another employee's data.
  • HR_Manager: (1) any employee's record within this company, (2) this company's policy documents, (3) the general Egyptian Labor Law knowledge base — never another tenant's data.

For HR, a message that expresses intent to generate a document (e.g. "generate a contract for Ahmed at 10,000 EGP") is routed internally to the same flow as POST /documents/generate (§4.5), with any missing fields returned as structured input prompts inside the chat reply.

8. Standard Error Format

All errors follow the same envelope:

{
  "error": "error_code",
  "message": "Human-readable description",
  "status": 400
}
StatusMeaning
400Bad request / validation error
401Missing or invalid token
403Authenticated but not authorized for this resource/role
404Resource not found (or belongs to another tenant → treated as not found, not 403, to avoid leaking existence)
422Business-rule violation (e.g., insufficient leave balance)
429Rate limit exceeded
500Internal server error

9. Rate Limiting

Endpoint groupLimit
/chat/ask20 requests / minute / user
/documents/generate10 requests / minute / user
All other endpoints100 requests / minute / user

Rate-limited responses return 429 with a Retry-After header (seconds).

10. Tenant Isolation Rule (applies to every endpoint above)

  1. company_id is never accepted from the client — it's extracted server-side from the JWT.
  2. Every database query filters by company_id in addition to any other WHERE clause.
  3. Requesting a resource (employee_id, doc_id, request_id, etc.) that exists but belongs to a different company returns 404, not 403 — this prevents leaking the existence of other companies' data.
  4. The RAG vector index used by /chat/ask is partitioned per company_id, so retrieval can never cross tenant boundaries.
